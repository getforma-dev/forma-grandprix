# Forma 3.1 performance decisions

Decision date: 2026-10-24. These are prospective release decisions, not a claim
that an existing failed campaign passed or that 3.1 has been published.
Implementation, exact-source review, CI, packed qualification and release
evidence remain required.

The maintainer explicitly authorized promotion and release using product-wide
judgment, superseding the earlier instruction to block release until both
FORMA-259 and FORMA-260 met their original numerical targets. The maintainer
also proposed treating occasional startup tasks up to 55 ms as exceptions.
The detailed limits below implement that delegated judgment; they are Forma
product budgets, not web standards or a statistical claim about every device.

## What the release protects

Forma supports browser applications, native Rust SSR, static routes with no
JavaScript and selective island adoption. We prioritize useful interactive
behavior, small delivery and server costs, and predictable ownership across
these modes. Browser-only table creation is a supported workload and a real
weakness; it is not a complete measure of the stack.

Correctness, security, typed sinks, initial no-write adoption, node identity,
listener ownership, cleanup, deployment integrity and public API behavior are
not exchanged for benchmark throughput. Experimental changes that violate
those contracts are excluded. Compression remains opt-in because its transfer
savings carry measured CPU and tail-latency costs.

## FORMA-259: effect speed and delivery cost

Select the simpler supplied-node effect design for final qualification, with
the startup-subscription cleanup repair and existing reporter/browser controls.
Do not select the native-bootstrap prototype: its fixed feasibility screen
showed a severe creation-throughput regression despite correctness controls.

In retained Linux campaign 40136359826, the simpler flat design improved writes
about 68%, fan-out 161% and effect creation 218% against published Forma in the
same campaign. Its ratios to the pristine alien-signals 3.1.2 control in the same candidate
trial were 93.666%, 76.314% and 101.545%, with a nine-workload geometric mean
of 94.977%. The original 80% fan-out target
was not achieved in that campaign. An earlier 80.237% result is retained too;
neither result replaces the other.

The diagnostic benchmark application was 8,532 bytes Brotli, versus 8,652 for
published Forma and 8,417 for the independently improved mainline application.
The final integrated source must be measured again. Allowing a small, explicit
delivery cost for these substantial public-effect gains is preferable to
adding complex lifecycle machinery merely to satisfy a relative microbenchmark.
No adopted-only speedup is inferred from public-effect results.

The local integrated build at `9ac07a446ebe8aaad407a895fa8aaece189bc69e`
measures 25,347 raw / 9,316 gzip / 8,498 Brotli bytes for the unchanged benchmark
application. That is 154 Brotli bytes below published Forma and 81 above the
retained improved-main application. It does not replace the diagnostic
candidate's identity. The fresh Linux campaign below measures this exact source.

The fixed final client campaign [40140319634](https://github.com/getforma-dev/forma/actions/runs/40140319634)
measures that integrated `9ac07a44` source against published Forma and pre-effect
main `f5be8647` on one VM. Writes improve 70.74%, fan-out 145.77% and effect
creation/disposal 251.34% versus published Forma. Same-trial pristine 3.1.2
ratios are 86.030%, 71.645% and 85.206%, with an all-nine geometric ratio of
86.621%. The original fan-out target still fails. The application bytes above
match the hosted build. The [complete report and independent assessment](https://github.com/getforma-dev/forma/tree/f98a089de2c2b4850ee5a2b74fafc994076762f3/benchmarks/grand-prix/evidence/2026-10-24/client-final)
retain all operations, five measured samples after two warmups, means, sample
standard deviations, source identities and original archive authentication.

Accept the measured batching cost explicitly: throughput is 13.79% below
published Forma and 6.93% below pre-effect main. Four selected samples cluster
below four published samples, so this is not dismissed as one outlier or
explained away by overlapping spreads. The batch primitive and workload are
unchanged; the changed effect lifecycle lies on the dependency/callback path,
but these sequential observations do not isolate a cause. The substantial
public-effect gains justify this tradeoff for 3.1. They do not establish that
every reactive workload improved or that adopted islands received the same gain.

The before/after island-adoption comparison ran once as fixed ABBA campaign
[40146688695](https://github.com/getforma-dev/forma/actions/runs/40146688695)
(PR #197): published-baseline main `f5be8647` (A) against selected `44835efa` (B),
both measured with B's unchanged 1,000-binding `island.mjs`, five warmups and
fifteen samples per leg, on three dedicated CPUs of one hosted VM. Every leg
adopted with zero writes and passed the script's update and disposal checks.
Mean adoption time is 8.587 ms (A) versus 8.927 ms (B): 0.340 ms or 3.96%
higher, and both B legs are above both A legs. Medians are 8.85 and 8.90 ms, and
the difference is smaller than either source's sample standard deviation
(1.60 and 1.88 ms). Mean single-signal update time is 1.247 ms versus 1.140 ms;
one A outlier of 7.1 ms drives that difference, and the medians are 1.0 and
1.1 ms. An earlier local quiet run showed the same direction for adoption
(4.573 to 4.693 ms). Initial strict adoption bindings use the raw engine, so this
benchmark is a regression control rather than a measure of the optimized public
path. The ticket's "no regression in adoption time" criterion is therefore not
demonstrated. This release accepts the small measured adoption cost alongside
the public-effect gains, and does not claim an adoption speedup.

The selected integration at `32d109071c11f8ce4f040f5f8bc7c6d3798ba1f6`
measures 49,212 gzip bytes for the core ESM import graph and 28,304 for the
indexed island route's Forma allocation. It exceeds the old ceilings by 310
and 204 bytes. Set the new ceilings to 49,414 (+512) and 28,420 (+320), leaving
202 and 116 bytes of headroom for this exact build. The four other package
gates and all total-route JavaScript limits remain unchanged. Against the
retained current-main measurements of 48,818 and 28,055, the integrated costs
are 394 and 249 bytes respectively. A size-budget revision is an explicit
tradeoff, not a claim that the old limits passed. Any subsequent shipped
source must be measured and pass the new ceilings without an automatic reset.

## FORMA-260: retain stable rows and record the missed target

Retain the reviewed default row construction and native event ownership.
Do not ship the literal/fresh-event compiler prototype in this release.
The original create-1,000 target of at most 1.10 times same-session vanilla
remains unmet and is accepted as a documented limitation for 3.1.

The latest literal-only local screen measured 19.80 ms versus vanilla 16.82 ms,
with overlapping baseline/candidate spreads and a slower selection result.
The later fresh-event prototype has no timing result, introduces a
restricted compiler contract, and increases its full diagnostic app from
8,473 to 8,844 bytes Brotli. Neither is justified as a late compatibility change.
Final reracing must retain all nine operations and identify material regressions;
accepting the existing creation gap is not permission to conceal new regressions.

The integrated campaign 40140319634 retains that gap: create-1,000 is
44.56 ± 4.11 ms versus same-trial vanilla 26.14 ± 2.40 ms, or 1.7047 times
vanilla. Published Forma is 44.82 ms and pre-effect main 43.48 ms. Selection
is 1.36 ms versus published 0.68 ms, with the increase already present on
pre-effect main at 1.58 ms. Clear is 6.00 ms versus main 4.60 ms (+30.43%)
and published 6.04 ms; update-every-tenth is 7.34 ms versus main 6.42 ms
(+14.33%) and published 7.90 ms. Accept these observed costs alongside the
stable default row path for this release, retain them in the report and future
row work, and make no blanket non-regression claim. The same campaign also
records improved replacement and swapping; no single aggregate erases the
adverse operations. A later source change needs its own relevant verification;
these timings remain bound to `9ac07a44`.

Future work should evaluate an explicit compiler template/event design or
large-list rendering strategy with its own contract and workload evidence.
Solid documents cloned templates and delegated versus native events; Svelte
documents delegation's propagation/order implications and compiler template
strategies. These are useful design precedents, not drop-in algorithms with
identical Forma semantics:

- [Solid JSX compilation](https://docs.solidjs.com/concepts/understanding-jsx)
- [Solid event delegation and native events](https://docs.solidjs.com/concepts/components/event-handlers)
- [Svelte event delegation](https://svelte.dev/docs/svelte/basic-markup#Events-Event-delegation)
- [Svelte compiler options](https://svelte.dev/docs/svelte/svelte-compiler#CompileOptions)

## Startup: bounded exceptions

Fifty milliseconds remains the engineering target and the threshold used to
record long tasks and excess blocking. A 55 ms task contributes 5 ms of blocking
time above that threshold; it can still delay an input that arrives during the
task. Aggregate blocking and actual interaction behavior therefore matter in
addition to a single maximum. [Google's TBT guidance](https://web.dev/articles/tbt)
distinguishes those measures and recommends field INP for real-user responsiveness.

For each route's fixed twenty cold Lighthouse visits, the prospective startup
policy permits at most two positively identified application startup tasks in
at most two visits above 50 ms, with each task at most 55 ms and total excess
above 50 ms at most 10 ms across the twenty visits. A task containing input
dispatch or lacking the required positive source/trace binding is ineligible.
The full task wall time is counted; no overhead is subtracted.

Independent activation/input observations originally retained the strict 50 ms
ceiling (policy `N3-cold-start-bounded-v1`). On 2026-10-25 the maintainer
extended the same bounded allowance to them as `N3-cold-start-bounded-v2`. An
observer task above 50 ms is admitted only up to 55 ms, by duration alone (an
observer task carries no trace attribution, so it may be one of the observer's
own interaction tasks, which the Lighthouse branch never admits), and draws on
the route's single
budget together with the Lighthouse exceptions: at most two exceptional tasks
of either kind in at most two of the twenty visits, at most 10 ms total excess.
A task over 55 ms is refused before the budget is counted. Any observer long
task still disables the L-66 browser-internal correlation for the whole
campaign, and the injected 110 ms controls keep their strict 50 ms oracle.
This decision followed packed run
[40149237051](https://github.com/getforma-dev/forma/actions/runs/40149237051),
which failed on one 53 ms observer task in tenant-login visit 2, one of forty
visits. Its only other tasks above 50 ms were a proven 52.0 ms Lighthouse task
(tenant-login visit 18) and a proven 51.1 ms one (islands-100 visit 14). The
same client bytes had passed run 40147411736 with no observer task. That
failure remains failed; v2 is prospective and needs a fresh campaign.

All islands must activate and respond, errors must remain absent, the existing
500 ms response-after-paint bound and p95 TBT below 200 ms remain unchanged.
Raw tasks, whole-page metrics, the 50 ms target-miss flag, the browser profile,
collectors and existing browser-work attribution remain intact. This is an
acceptance-policy change, not a task filter or a global 55 ms redefinition.

The retained failed campaign 40134699981 contained three source-bound
`drainLoads` timer tasks of 50.275, 50.984 and 54.358 ms. Login had two affected
visits and 1.259 ms total excess; islands had one and 4.358 ms total excess.
All forty independent probes had no long tasks. Those observations motivate
evaluating bounded startup cost; they do not prove a population-tail rate or
that an arbitrary real interaction could never be delayed.

The new policy must be versioned and tested before a fresh exact-source
campaign. Published 3.0 records remain validated under their original strict
policy, and failed historical runs remain failed. Positive and refusal
controls must cover the boundary, repeated exceptions, aggregate excess,
input dispatch, missing/ambiguous attribution and historical-policy isolation.

Longer-term scheduling work should use actual task boundaries. Merely splitting
functions does not yield to input. Browser scheduling APIs can yield between
independent work units, but Forma's atomic adoption and cancellation contracts
must be preserved. [Task splitting guidance](https://web.dev/articles/optimize-long-tasks)
and [scheduler.yield](https://developer.chrome.com/blog/use-scheduler-yield)
inform that work; this release does not introduce an unqualified scheduler.

## Completion evidence

These decisions do not supply test results. Final closure still requires the
integrated source, updated reports and ticket dispositions, independent review,
all applicable CI, a fresh qualified Linux rerace and packed release checks,
followed by the existing release-candidate publication and active burn-in
requirements. A successful release must disclose the original missed targets
and accepted costs alongside the measured improvements.
